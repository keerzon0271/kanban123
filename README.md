# Инструкция по работе с Kanban-доской

## 1. Зачем используется Kanban-доска в проекте
Kanban-доска — это инструмент для визуализации процесса разработки. Она помогает команде:
*   Видеть все задачи в одном месте и понимать, кто чем занят.
*   Ограничить количество одновременно выполняемой работы, чтобы не терять фокус.
*   Оперативно выявлять "узкие места" (например, когда задачи скапливаются на этапе тестирования).
*   Обеспечить прозрачность прогресса как для команды, так и для заинтересованных лиц.

## 2. Что означает каждая колонка
*   **Backlog (Бэклог):** Полный список всех задач проекта. Здесь они хранятся, пока команда не решит взять их в работу. Эта колонка постоянно пополняется новыми идеями и требованиями.
*   **To Do (К выполнению):** Список задач, которые запланированы к выполнению в ближайшее время (например, в этом спринте). Они уже приоритезированы и готовы к старту.
*   **In Progress (В работе):** Задачи, над которыми команда активно работает прямо сейчас. Важно, чтобы количество задач здесь было минимальным.
*   **Review (Проверка):** Задача выполнена и ожидает проверки. Это может быть код-ревью (для разработчиков), приемка дизайна или тестирование (для QA-инженеров).
*   **Done (Готово):** Задачи, которые полностью завершены, проверены и приняты. Критерий попадания сюда — работа больше не нужна.

## 3. Как создаётся новая задача
1.  Внизу нужной колонки (обычно Backlog) нажать кнопку **"+ Add item"**.
2.  Ввести название задачи и в выпадающем списке выбрать **"Create new issue"**.
3.  Справа откроется панель:
    *   В поле **Role** выбрать команду-исполнителя (Backend, Frontend и т.д.).
    *   В поле **Priority** выставить приоритет (High, Medium, Low).
    *   В поле **Assignees** назначить ответственного, когда он будет известен.
4.  Открыть созданную Issue (нажать на ее название), чтобы добавить подробное описание: что нужно сделать, чек-лист, ссылки на макеты или связанные User Stories.

## 4. Как задача проходит путь от Backlog до Done
Типичный жизненный цикл задачи выглядит так:
1.  **Backlog:** Менеджер или аналитик создает задачу, описывает требования.
2.  **To Do:** На планировании команда решает делать задачу в этом спринте. Карточка вручную перетаскивается мышкой в эту колонку.
3.  **In Progress:** Назначенный разработчик (или дизайнер) приступает к работе и перетаскивает задачу сюда. Факт начала работы зафиксирован.
4.  **Review:** Когда разработка закончена и создан Pull Request (или готов макет), задача перетаскивается в колонку `Review`. Сюда же заходит QA-инженер для тестирования.
5.  **Done:** Если в задаче не найдено ошибок, она перетаскивается сюда и считается завершенной.

## 5. Как распределяются задачи между ролями
При создании каждой задаче в обязательном порядке присваивается пользовательское поле **Role**. Оно может принимать одно из 5 значений:
*   **Analytics (Аналитика):** Написание ТЗ и спецификаций.
*   **Design (Дизайн):** Создание макетов и графики.
*   **Backend (Бэкенд):** Серверная логика, API, базы данных.
*   **Frontend (Фронтенд):** Пользовательский интерфейс и его логика.
*   **QA (Тестирование):** Тест-кейсы, поиск багов, приемка.

Это позволяет фильтровать доску и видеть, например, "все задачи для бэкенда" или "весь дизайн на проверке".

## 6. Как отслеживать прогресс проекта
*   **Визуальный осмотр:** Главный индикатор — Kanban-доска. Если колонка `Review` растет, а `Done` нет, значит, тестирование не справляется.
*   **Использование Assignees:** Видно, у кого из сотрудников наибольшая нагрузка (много задач в `In Progress`).
*   **Фильтры и вьюшки:** В проекте можно создать отдельные вкладки-представления (вкладка `View`), например, "Работа бэкенда" или "Приоритетные задачи". Нажав `+`, выбрав `View` и `Board`, можно систематизировать задачи только по ролям.
*   **Burndown-чарты:** В GitHub Projects v2 есть встроенный график прогресса, который показывает, сколько задач закрыто и сколько осталось.
